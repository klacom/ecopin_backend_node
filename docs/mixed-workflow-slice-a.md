# Mixed Workflow — Slice A implementation record

## Scope and status

The first Slice A increment implements the lifecycle/SLA foundation and its scheduler integration. It has been tested locally; it has not been deployed to Supabase. Atomic dispatch, fleet flags, classified failure release, access controls, clustering guards and mobile authority changes remain subsequent Slice A increments. Do not enable the foundation as a complete Mixed Workflow rollout.

Policy authority: [the user's finalized policy record](../mixed_workflow_phase0_results_2026-10-08.md). The historical reset and severity tier boundaries are accepted. The policy specifies accelerated High-tier maturation but no numerical duration. Activation therefore requires that duration explicitly; 12 hours appears only in test fixtures and is not a production default.

## Implemented behavior

- Low: 0–33; Medium: 34–66; High: 67–100; missing severity remains explicitly unknown and uses normal maturation.
- Normal maturation defaults to the plan's 24 hours; SLA breach uses the existing `sla_threshold` JSON hours (currently 48). High maturation must satisfy `0 < high < normal < SLA <= 168`.
- Activation archives unresolved reports' original created time, deadline and flag in `workflow_private.historical_sla_reset`, preserving `reports.created_at`.
- One persisted deployment timestamp becomes those unresolved reports' `sla_started_at`; their effective deadline becomes that timestamp plus the configured SLA. Existing closed reports are not reset or retrospectively declared cleaned.
- Activation retries return the existing timestamp and reset zero reports. They do not silently change maturation settings.
- New reports start their clock at insertion. Later severity edits change their maturation tier but cannot restart the SLA clock or extend the snapshotted deadline.
- Lifecycle precedence: terminal report status, task claim, cluster membership, breach deadline, maturation, fresh. Maturation/breach timestamps persist across assignment, release and closure.
- Trigger changes and audit inserts are atomic. A completed hourly run has a durable `LIFECYCLE_RUN_COMPLETED` audit even if no reports changed.
- Advancement uses a transaction advisory lock; a competing worker returns `skipped=true`. Locked report rows are skipped until a later tick. This is lifecycle-worker coordination, not proof of atomic dispatch correctness.
- The scheduler is registered by `src/index.js`, defaults to hourly in `Asia/Manila`, prevents overlapping local ticks, and stops on shutdown. It is opt-in through `REPORT_LIFECYCLE_ENABLED=true`.
- The JavaScript threshold getter delegates to the canonical JSON reader. Legacy detection counts reflect database changes even when an audit request fails.
- Lifecycle analytics count historical `breached_at`, including closed reports, and use `sla_started_at` for the reporting cohort. Task queries use the live `estimated_duration_min` and `cluster_ids` columns. Database errors propagate instead of rendering false 100% compliance.

## Migration and activation contract

Migration: [20261008064832_report_lifecycle_foundation.sql](../migrations/20261008064832_report_lifecycle_foundation.sql). Its filename was generated by the Supabase CLI and moved to this repository's existing `migrations/` directory. This repository is not a newly baselined Supabase CLI migration project; do not `db push` the lone migration as though it reconstructs the existing database.

The migration adds columns/functions/triggers without activating the historical reset. It replaces the old detector with a baseline-aware wrapper, which rejects calls before activation. Apply and activate in the same planned deployment window, after the remaining Slice A readiness gates and the numerical High-tier window are settled.

Activation is a service-role-only RPC:

```js
await supabaseAdmin.rpc('activate_report_lifecycle', {
  high_maturation_hours: approvedHighHours,
  normal_maturation_hours: 24
});
```

Use the returned `activatedAt` as the deployment baseline. It is generated by PostgreSQL, not passed from an application clock. Activation locks report writes while it snapshots and establishes the baseline. It includes existing `unresolved` reports with active task/cluster links; their derived state remains dispatched/clustered and their new SLA clock still starts at deployment.

After activation, configure:

```dotenv
REPORT_LIFECYCLE_ENABLED=true
SLA_DETECTION_CRON=0 * * * *
SLA_DETECTION_TIMEZONE=Asia/Manila
```

Verify registration in Node host logs and a `LIFECYCLE_RUN_COMPLETED` audit on the deployed revision. The SLA status endpoint's last-run fields still describe its existing in-memory manual-run state; they are not proof of scheduler execution. Use the durable audit evidence for this increment.

The ordinary `is_outlier` column is temporarily derived by the trigger for active legacy consumers. It becomes true for unclaimed maturing/breached reports. The column must not be dropped until those consumers migrate. Trigger functions use a private schema and fixed empty search paths; public operational RPCs are SECURITY INVOKER and executable only by service_role. Existing table grants/RLS findings remain work for Slice A's authorization increment.

## Verification

```powershell
npm test -- --runInBand
npm run test:db:lifecycle
```

The database runner expects the isolated Docker container `ecopin-slice-a-postgres` with PostgreSQL 17 and a local postgres superuser. It creates a uniquely named fixture database, runs bootstrap/migration/assertions, checks a competing worker from a second connection, and drops only that fixture database. It reads no Supabase credentials.

Observed: 40 Jest tests passed; 31 PostgreSQL assertions passed; two-connection advisory-lock test passed. Database fixtures use the live report status enum and legacy deadline trigger shape. They do not reproduce the complete production notification, RLS, spatial or clustering environment. Target migration/staging verification is still required.

## Recovery

Before activation, leave `REPORT_LIFECYCLE_ENABLED` unset to prevent the new schedule running. After activation, setting it false stops scheduling on restart but does not undo the database triggers or restore deadlines. Do not roll the application back to an age-only detector after resetting the baseline.

Preserve the deployment marker and reset archive. Any database reversal must be reviewed using the archive and postactivation reports; blindly restoring old deadlines or rerunning a backfill would violate the accepted policy. Prefer a forward correction, with the scheduler disabled while investigating. No automatic destructive rollback is included.
