# Verification digest storage and issuance

Migration `20261011154236_store_verification_digests_and_bound_issuance` and its backend change issue UUIDv4 links while sending only a SHA-256 digest to Postgres. New rows have a null raw-token field, a unique digest and a database-generated creation/expiry timestamp. Lookup hashes the canonical lowercase UUID; there is no raw-token fallback. Before deployment all eight legacy token rows were expired and no active link needed compatibility. Their existing values remain unchanged pending retention cleanup.

The service-only invoker issuance function locks the user's current profile and defers missing or already verified accounts. That lock serializes requests across application processes. Creation of any token in the previous 60 seconds defers another issuance; after that interval a later resend can succeed. The database accepts TTLs from 1 to 24 hours. Null issuance never reaches SMTP. Anonymous and authenticated table privileges are revoked in addition to existing RLS.

Absent, already verified, deferred and successfully issued resend requests return the same response. Auth, database and SMTP failures also return that response, with a generic internal error log. This closes the status/body distinction; it does not establish indistinguishable timing or a full bot defense. Existing first-page-only Auth user lookup, per-IP throttling, issued-email binding, old-row retention and real-user delivery remain unfinished S02 work. Auth confirmation and atomic profile/token completion remain separate operations, as described in the completion document.

Verification on 11 October 2026: 173 backend tests in 27 suites passed. The new service tests first reproduced raw issuance and missing deferral (two failures, one existing error-handling pass). Fresh isolated PostGIS passed 21 issuance plus 14 completion assertions before and after rollback/reapplication. Two real connections showed an observed profile-lock wait and exactly one issuance; moving the fixture outside the cooldown permitted a later issuance. Rollback preserved the digest-row fingerprint and reapplication passed.

All 35 live rollback-only assertions passed. Counts, existing token values, verification flags and settings stayed unchanged. No real email was sent, no Auth account was created or confirmed, and no test token persisted. Source matches the single live ledger statement exactly: MD5 `6ce995ea0e3d427a1dce2ff665b72e71`.

Real HTTP denied anonymous issuance and token-table reads (401/42501), returned null for service issuance with a null user, and kept unknown/malformed local verification links at 400 with no-store responses. No new security advisory appeared; the existing limited-owner map-view and leaked-password-protection advisories remain.

Run `node scripts/test-email-issuance.mjs` for the fresh drill. The rollback deliberately removes only the issuance function; it retains digest data, schema/index and client privilege hardening because a digest cannot reconstruct the original delivered secret. Revert backend callers before dropping the function. Existing digest links require the new backend or a resend after rollback. Old backend code can explicitly store a new UUID for emergency compatibility; it cannot redeem links issued through the digest flow. Prefer forward repair over returning to raw storage.

Hashing uses the existing [Node crypto API](https://nodejs.org/api/crypto.html#cryptocreatehashalgorithm-options). Privilege restrictions follow [Supabase column/table access guidance](https://supabase.com/docs/guides/database/postgres/column-level-security).
